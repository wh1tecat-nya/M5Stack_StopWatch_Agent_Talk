# 既存のすみへの低遅延経路の調査

調査日: 2026-11-07。既存のdot「すみ」との会話を維持し、録音・音声再生はStopWatch本体で行う。ハブにスマートフォン、ブラウザー、PCを使う構成も対象とする。

## 実機ログから分かる範囲

USBシリアルの `?` で読み出した、端末に保存済みの成功3件。単位は秒。受付・返信・再生キュー投入は左ボタンを離してからの経過時間、合成だけは処理時間。

| サンプル | アップロード受付 | 返信ヘッダー受信 | 本体TTS合成 | 再生キュー投入 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1.693 | 67.149 | 2.271 | 69.504 |
| 2 | 1.627 | 216.938 | 3.825 | 220.807 |
| 3 | 1.564 | 439.719 | 2.532 | 442.304 |

3件ともポーリングエラーは0件。返信なしの最終確認からヘッダー受信までは、それぞれ1.377秒、3.222秒、3.030秒。端末側の返信確認周期やTTSだけでは、全体の待ち時間を説明できない。主な空白は受付後からChatGPT側の返答が届くまでにある。ただし、このログだけではChatGPT側の起動待ち、モデルの処理、ツール呼び出しを分離できない。

従来のイベント経路は、文字起こし→MCPイベント→すみのクラウド作業→返答ツール→本体TTS。MCP Eventsは更新を契機に作業を行う仕組みで、調査した仕様に会話の応答時間の保証は見つからなかった。[公式仕様](https://developers.openai.com/plugins/build/mcp-events)

## 第一候補: プラグインUIを既存のすみの会話で開く

OpenAIの公式資料に、MCP Appsの `ui/message` と互換API `window.openai.sendFollowUpMessage` が記載されている。プラグインUIから会話へフォローアップを送信できる。[UIブリッジ](https://developers.openai.com/plugins/build/chatgpt-ui)、[APIリファレンス](https://developers.openai.com/plugins/reference)

Plugin Extensionsには会話の横に開くパネルと、現在の会話へのメッセージ送信機能もある。通常のインラインUIより、中継用の画面を開き続ける用途に合う可能性がある。[Extensions](https://developers.openai.com/plugins/build/extensions)

想定経路:

```text
StopWatchのマイク → Wi-Fi → 既存Workerで文字起こし
  → 開いているプラグインUI → ui/message → 既存のすみの会話
  → submit_stopwatch_reply → Worker → StopWatchの本体TTS・スピーカー
```

音声機器はStopWatchだけを使う。ハブは文字の受け渡しを担う。MCPイベントによる起動を経由しないため、現行の待ち区間を減らせる可能性がある。返答は既存の返答ツールで回収する設計なので、UIがモデルの回答本文を直接取得できると仮定する必要はない。

未検証事項:

- dotsの既存のすみの会話で、UIまたは会話パネルが開けるか。
- 端末ボタンを離した発話を、受信したUIから送信できるか。ホストが画面上での操作を要求する可能性も確認する。
- すみの通常応答で、既存の返答ツールが使えるか。
- ハブの画面を背面にしたとき、UIの受信・送信処理が継続するか。
- 実際の応答時間、二重送信防止、切断時の回復。

採用前の小規模検証では、まずホストの対応機能を確認し、短い1往復を計測する。端末の発話IDを全区間で引き継ぎ、受付、UI受信、会話送信、返答ツール受信、再生開始を分けて記録する。イベント経路への自動併送は、すみの二重応答を招くため行わない。

これは公式に定義されたUI機能を使う候補であり、既存dotを直接呼び出す公開REST APIが見つかったという意味ではない。プラグインUI経路の互換性・遅延は未実証。後述のChrome拡張経路では、既存すみとの実機往復を確認した。

### 実装した試作

`0004_ui_bridge.sql` と `open_stopwatch_bridge` を追加した。接続先でツール一覧を更新した後、既存のすみの会話で「StopWatchの会話中継を開いて」と伝え、表示された画面で「開始」を押す。会話画面でのUI表示と `ui/message` の対応が必要で、対応していないホストでは開始できない。

開始中の画面は1秒間隔で発話を受け取る。セッションは45秒の期限を更新し、別の画面による同時利用を拒否する。開始中に受け付けた発話だけをUI経路へ固定し、イベント経路へ重複配送しない。同じ発話の取得は1回だけで、前の返答を待ってから次を取得する。送信結果が不明な場合は自動再送しない。停止後の新しい発話は従来経路へ戻る。閉じた場合は最大45秒後に戻るが、既にUIへ割り当てた発話をイベントへ再配送することはない。

本体での録音・読み上げと期限なしの会話履歴は維持する。ログには文字起こし完了、UI取得、会話送信受付、返答到着までの経過時間を追加した。模擬ホストとローカルWorkerの6テストが通り、公開Workerへ反映済み。実際のdotsで試したところ中継UIが表示されず、この経路の応答時間は計測できなかった。

## 第二候補: PCで公式のすみ通話を音声中継

公式資料は、既存のdotの会話にある電話ボタンから、デスクトップアプリまたはデスクトップブラウザーで通話できるとしている。同じdotは接続した各連絡手段で継続する。[dotsの連絡方法](https://learn.chatgpt.com/docs/dots/channels)

```text
StopWatchのマイク → Wi-Fi音声ストリーム → PCの仮想マイク
  → 公式のすみ通話 → PCの仮想出力
  → Wi-Fi音声ストリーム → StopWatchのスピーカー
```

PCは音声の経路だけを担う。マイク・スピーカーはStopWatch本体を使う。現行のMCPイベントとファイル単位の文字起こしを通らずに、公式通話へ音声を渡す構想。仮想音声機器の選択、ストリームのバッファ、切断処理、エコー、端末のマイクとスピーカーの切り替えを実装・実測する必要がある。公式通話の存在は確認済みだが、この構成の動作・遅延は未検証。

スマートフォンの専用アプリをハブにする場合も、別アプリであるChatGPTの通話音声へ入出力を接続できるかが課題になる。Wi-FiやBLEでスマートフォンへデータを渡せることだけでは、公式通話への接続を保証できない。現時点ではPC案より優先しない。

## 補助候補: Chrome拡張で通常の会話画面を中継

既存すみの画面では中継UIのiframeが読み込まれず、DB上の中継セッションも0件だった。「開いた」というすみの返答だけでは開始を確認できなかったため、Chrome拡張と別の中継ページを使う試作を追加した。

Chrome拡張で文字起こしを既存すみの入力欄へ入力・送信し、返答は既存の `submit_stopwatch_reply` でWorkerへ戻す。画面の別の返答を誤取得しないよう、回答本文のDOM抽出は行わない。音声の録音・読み上げは本体側に残る。[拡張の導入と権限](../browser-extension/README.md)

これはブラウザーの通常画面を操作する独自実装で、公式のdot送信APIではない。選択したタブだけへの一時的なアクセスを使い、全サイトへの常時アクセスは要求しない。中継ページは既存の履歴ログインを使い、APIキー・オーナーキー・ChatGPTのCookieを拡張へ渡さない。タブ・接続元の制限、下書き・添付の保護、二重送信防止、Worker側の認証、接続タブを保存してから前面に出す順序を含む15テストが通過した。接続後、StopWatchの発話と既存すみの返答が会話画面に表示され、本体からの読み上げもユーザーが確認した。中継ページとすみのタブを開き、PCを起動したまま使う必要があり、画面構造の変更への追従も必要になる。

### Chrome拡張経路の実機計測

2026-11-07、発話ID `4e82967d33f3fa90af75b163b8512888` の1往復を計測した。認識結果は「聞こえる?」、既存すみの返答は「うん、聞こえてるよ！」。ユーザーが本体から返事を聞いたことを確認した。

端末ログの時刻は左ボタンを離した時点からの経過時間。合成だけは処理時間。

| 端末側の計測点 | 秒 |
| --- | ---: |
| アップロード受付 | 1.600 |
| 返信なしの最終確認 | 25.704 |
| 返信ヘッダー受信 | 27.054 |
| 本体TTS合成の処理時間 | 1.949 |
| 再生キュー投入 | 29.056 |

ポーリングエラー0件、HTTP 200。再生キュー投入は物理的な発音開始そのものを測った値ではない。

Workerログは別の起点で、Workerが発話を作成した時点からの経過時間。

| Worker側の計測点 | 秒 |
| --- | ---: |
| 文字起こし完了 | 1.522 |
| 中継ページが発話を取得 | 2.054 |
| すみの会話画面への送信受付 | 4.089 |
| 返答ツール受信 | 25.281 |

会話画面への送信から返答ツール受信までは21.192秒。この区間が今回の待ち時間の大半で、モデルの処理とツール呼び出しをさらに分離するログはない。従来イベント経路の直前の成功例は再生キュー投入まで309.733秒だったが、発話や会話状態が異なるため、今回の29.056秒を一般的な改善率や保証値にはしない。

## 調査対象から外したAPI

Workspace Agentsには外部から起動するAPIがあるが、公開済みWorkspace AgentのAPIチャネルIDを指定する方式。既存の個人dotを指定する手段は、この資料では確認できない。そのまますみへの直接経路として採用できない。[Workspace Agents API](https://developers.openai.com/workspace-agents/trigger-runs)

## 判断

左ボタン用途は、実機往復を確認できたChrome拡張経路を利用する。今回の再生キュー投入まで約29秒のうち、約21秒が会話送信後のすみ側の応答区間に残る。継続的な低遅延はまだ保証できず、通話用途のPC音声中継は未実装。中継を開始していない間は、会話経路は従来のイベント方式になる。
