# 既存のすみへの低遅延経路の調査

調査日: 2026-11-07。既存のdot「すみ」との会話を維持し、録音・音声再生はStopWatch本体で行う。ハブにスマートフォン、ブラウザー、PCを使う構成も対象とする。

## 実機ログから分かる範囲

USBシリアルの `?` で読み出した、端末に保存済みの成功3件。単位は秒。受付・返信・再生キュー投入は左ボタンを離してからの経過時間、合成だけは処理時間。

| サンプル | アップロード受付 | 返信ヘッダー受信 | 本体TTS合成 | 再生キュー投入 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1.693 | 67.149 | 2.271 | 69.504 |
| 2 | 1.627 | 216.938 | 3.825 | 220.807 |
| 3 | 1.564 | 439.719 | 2.532 | 442.304 |

3件ともポーリングエラーは0件。返信なしの最終確認からヘッダー受信までは、それぞれ1.377秒、3.222秒、3.030秒。端末側の返信確認周期やTTSだけでは、全体の待ち時間を説明できない。主な空白は受付後からChatGPT側の返答が届くまでにある。ただし、このログだけではChatGPT側の起動待ち、モデルの処理、ツール呼び出しを分離できない。

現行経路は、文字起こし→MCPイベント→すみのクラウド作業→返答ツール→本体TTS。MCP Eventsは更新を契機に作業を行う仕組みで、調査した仕様に会話の応答時間の保証は見つからなかった。[公式仕様](https://developers.openai.com/plugins/build/mcp-events)

## 第一候補: プラグインUIを既存のすみの会話で開く

OpenAIの公式資料に、MCP Appsの `ui/message` と互換API `window.openai.sendFollowUpMessage` が記載されている。プラグインUIから会話へフォローアップを送信できる。[UIブリッジ](https://developers.openai.com/plugins/build/chatgpt-ui)、[APIリファレンス](https://developers.openai.com/plugins/reference)

Plugin Extensionsには会話の横に開くパネルと、現在の会話へのメッセージ送信機能もある。通常のインラインUIより、中継用の画面を開き続ける用途に合う可能性がある。[Extensions](https://developers.openai.com/plugins/build/extensions)

想定経路:

```text
StopWatchのマイク → Wi-Fi → 既存Workerで文字起こし
  → 開いているプラグインUI → ui/message → 既存のすみの会話
  → submit_stopwatch_reply → Worker → StopWatchの本体TTS・スピーカー
```

音声機器はStopWatchだけを使う。ハブは文字の受け渡しを担う。MCPイベントによる起動を経由しないため、現行の待ち区間を減らせる可能性がある。返答は既存の返答ツールで回収する設計なので、UIがモデルの回答本文を直接取得できると仮定する必要はない。

未検証事項:

- dotsの既存のすみの会話で、UIまたは会話パネルが開けるか。
- 端末ボタンを離した発話を、受信したUIから送信できるか。ホストが画面上での操作を要求する可能性も確認する。
- すみの通常応答で、既存の返答ツールが使えるか。
- ハブの画面を背面にしたとき、UIの受信・送信処理が継続するか。
- 実際の応答時間、二重送信防止、切断時の回復。

採用前の小規模検証では、まずホストの対応機能を確認し、短い1往復を計測する。端末の発話IDを全区間で引き継ぎ、受付、UI受信、会話送信、返答ツール受信、再生開始を分けて記録する。イベント経路への自動併送は、すみの二重応答を招くため行わない。

これは公式に定義されたUI機能を使う候補であり、既存dotを直接呼び出す公開REST APIが見つかったという意味ではない。互換性・遅延は未実証。この調査では経路変更やすみへの試験メッセージ送信は行っていない。

## 第二候補: PCで公式のすみ通話を音声中継

公式資料は、既存のdotの会話にある電話ボタンから、デスクトップアプリまたはデスクトップブラウザーで通話できるとしている。同じdotは接続した各連絡手段で継続する。[dotsの連絡方法](https://learn.chatgpt.com/docs/dots/channels)

```text
StopWatchのマイク → Wi-Fi音声ストリーム → PCの仮想マイク
  → 公式のすみ通話 → PCの仮想出力
  → Wi-Fi音声ストリーム → StopWatchのスピーカー
```

PCは音声の経路だけを担う。マイク・スピーカーはStopWatch本体を使う。現行のMCPイベントとファイル単位の文字起こしを通らずに、公式通話へ音声を渡す構想。仮想音声機器の選択、ストリームのバッファ、切断処理、エコー、端末のマイクとスピーカーの切り替えを実装・実測する必要がある。公式通話の存在は確認済みだが、この構成の動作・遅延は未検証。

スマートフォンの専用アプリをハブにする場合も、別アプリであるChatGPTの通話音声へ入出力を接続できるかが課題になる。Wi-FiやBLEでスマートフォンへデータを渡せることだけでは、公式通話への接続を保証できない。現時点ではPC案より優先しない。

## 補助候補: Chrome拡張で通常の会話画面を中継

プラグインUIがdotsで動かない場合、ログイン済みのすみの画面に、Chrome拡張で文字起こしを入力・送信し、画面の返答を読み取ってWorkerへ戻す実装も考えられる。音声の録音・読み上げは本体側に残せる。

これはブラウザーの通常画面を操作する独自実装で、公式のdot送信APIではない。ログイン済みのタブを開き続けること、送信・返答完了の判定、重複防止、画面構造の変更への追従が必要になる。実装・検証はまだ行っていない。アカウントのCookieをWorkerへ渡す設計にはしない。

## 調査対象から外したAPI

Workspace Agentsには外部から起動するAPIがあるが、公開済みWorkspace AgentのAPIチャネルIDを指定する方式。既存の個人dotを指定する手段は、この資料では確認できない。そのまますみへの直接経路として採用できない。[Workspace Agents API](https://developers.openai.com/workspace-agents/trigger-runs)

## 判断

左ボタンの既存実装、ローカルTTS、吹き出し、履歴を活用しやすい第一候補から互換性を検証する。第一候補がdotsで利用できなければ、左ボタン用途にはChrome拡張、通話用途にはPC音声中継を検討する。いずれも低遅延を保証する数値はまだない。今回のファーム更新はアニメーションのみで、会話経路は現行のまま。
